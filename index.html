00 — In one paragraph

A multimodal LLM writes a short sequence of 6-DoF end-effector keyposes, a motion planner joins them with straight lines, and the agent looks at the result before writing the next sequence. No training, no demonstrations at test time, no primitive library. The agent decides how many keyposes a motion needs: one for a long free-space move, a few slow ones near contact, thirty when it draws.

Beyond the paper

It also writes code. One key at a time.

Asked for a program that prints the first ten Fibonacci numbers, the agent designs the shortest one it can, because every character costs a key press, types it on a physical keyboard, and presses F5 to run it.

02 — The observation

Manipulation is sparse.

We compressed 57,534 successful DROID teleoperation episodes into end-effector keyposes joined by straight lines. A grasp or release that takes 96 recorded actions needs about six keyposes, and over 91% of the travel lies on segments longer than 5 cm.

So an agent does not need to emit a dense stream of actions. It needs to say where the gripper should be next, and in what order.

03 — How it works

Look, measure, commit, look again.

  1. 1

    Observe

    The agent sees the current camera images, the arm state and the feedback from its last call.

  2. 2

    Query a few pixels

    It names the handful of pixels its next move depends on. A tool returns their 3D positions, tagged with how they were measured: triangulated, reconstructed or stereo.

  3. 3

    Write keyposes

    One call carries an ordered sequence of absolute 6-DoF poses with gripper commands, about one primitive such as approach, grasp, lift.

  4. 4

    Execute

    A motion planner follows straight lines between keyposes. The gripper acts only on arrival. If a segment is unreachable, the agent is told which keypose failed.

move_eef

Sparse, ordered keyposes

Absolute targets, so the agent never plans the waypoints of a long move. It sets the count, spacing and speed itself: fast across free space, short and slow near contact.

query_points

Sparse metric queries

No dense depth map. Each queried pixel is triangulated across views by epipolar matching, with a multi-view reconstruction as fallback; on the real robot, stereo depth. The agent sees the source and decides how much to trust it.

update_experience

Rules from its own rollouts

On hard tasks the agent reflects on a few practice rollouts and the lessons are merged into at most five bounded rules per task. No parameters are updated. Real-robot tasks use none of this.

one model call
# three keyposes: approach, descend and close, lift
move_eef(sequence=[
  {"pos": [0.412, -0.086, 0.180], "rpy": [180, 0, 90], "gripper": 1.0},
  {"pos": [0.412, -0.086, 0.062], "gripper": 0.0, "ramp": 12},
  {"pos": [0.412, -0.086, 0.220]}
])

Illustrative. Each keypose names only the dimensions it changes; the rest hold their value.

04 — Results

Best on two benchmarks,
at a twelfth of the cost.

Where it fails

Keyposes carry no force and no continuous feedback. On the real robot the ten failures are a shirt that slides along with the gripper, a peg insertion released before both pegs are seated, and drawings that would drive the wrist camera into the table. Each model call also takes seconds, so SOLVE suits quasi-static scenes. A learned low-level policy for contact-rich segments is the natural next step.
